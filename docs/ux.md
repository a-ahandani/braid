# UX notes

Ramulus borrows the interaction model that visual git clients have converged on: a three-pane layout with refs on the left, a lane graph in the middle and a detail or staging pane on the right, with every git operation reachable from a right-click on the thing it applies to. The notes below record where Ramulus deliberately departs from the common pattern and why.

## Decisions

- **It looks like a code editor, not a dashboard.** The palette, fonts, 22px rows, uppercase section headers, flat inputs, badge counters and the Codicons icon set follow the dark and light "modern" themes most developers already stare at all day, so nothing has to be learned about where the eye should go. Status letters and their colours (M, A, D, U) match the editor's source-control view for the same reason.
- **Actions are icons in the middle of the toolbar.** Pull, push, fetch, new branch, stash and pop sit centered as large icons with tooltips, grouped by what they touch: the remote, branches, the stash. The repository and branch stay on the left, search and panel toggles on the right. Pull's merge, fast-forward or rebase choice lives in a small menu beside it rather than a dropdown in the bar.
- **Starting outside a repository still opens the app.** If `npx ramulus` runs in a folder that is not a repository, the helper looks up to three levels down for repositories (skipping dot-folders and `node_modules`) and asks which ones to open as tabs. The list can be filtered by name, and Select all and Select none act on what the filter shows. They also stay listed under "This folder" in the picker. Starting inside a repository works the same way for repositories nested in its subfolders: the one you started in opens and stays in front, and the nested ones are offered beside it.
- **Repositories live in a left sidebar.** It can stay docked or auto-hide: unpinned, it slides out when the pointer reaches the left edge and slides away when the pointer leaves. Repositories can be pinned to the top; in helper mode pinned ones reopen on the next start. ⌘⇧A, the shortcut browsers use for tab search, focuses a filter that ranks name matches above folder matches, also searches recent repositories, and opens the best match on Enter.
- **Pull all and Fetch all act on every open repository.** Pull all is fast-forward only, so it can never create a merge commit or a conflict in a repository you are not looking at; each one it cannot fast-forward is listed with a one-sentence reason.
- **Rebasing with uncommitted changes just works.** The changes are stashed, the rebase runs, and they are put back. If putting them back conflicts, git keeps a copy in the stash and a banner walks through resolving and dropping it. A rebase can be undone from a bar that appears afterwards; the undo refuses if anything moved the branch since. A rebase that stops on conflicts keeps Continue and Abort.
- **A rejected push offers a way forward instead of an error.** When the remote has commits you do not, a dialog shows how many on each side and offers rebase then push, merge then push, or a force push with a lease. Force push asks once more, saying how many commits the remote loses.
- **AI help goes through the agent you already use.** Ramulus finds Claude Code, Codex, Gemini CLI or opencode on the PATH, asks before using one, and never needs an API key. Short answers that fill a field, a commit message or a branch name, come from the agent's non-interactive mode and land in the field for review. Anything that changes files happens in the agent's own interactive tool, running in a terminal panel at the bottom, so its approvals, history and commands work exactly as in the user's terminal. Ramulus pastes prompts there without sending them, so they can be edited first.
- **The checked-out branch is unmistakable.** In the graph its label is solid with a check mark and its commit is bold. In the branch list it comes first, tinted, with "checked out" beside it. In the toolbar it is a chip that opens a branch switcher; a detached HEAD turns the chip yellow.
- **Each branch section scrolls on its own**, capped at about a third of the window, so hundreds of tags never push Remote and Stashes out of view.
- **Local branches carry a laptop icon, remote ones a cloud**, so where a label lives is readable at a glance.
- **One sidebar entry per repository.** The + in the sidebar, the welcome screen and the palette all open the same picker: recent repositories, the system folder picker, or a typed path. Each tab keeps its own selection, filters and draft message. Only the visible tab watches its folder, so open tabs cost nothing while hidden and refresh when you return. The helper only touches repositories the user opened in this run, and remembers them in `~/.config/ramulus/recent.json`.
- **The message box sits above the file lists, with Changes above Staged**, so files move down into Staged as they are staged and the list being committed sits last, just under the files it came from.
- **The graph breathes.** Rows are 30px with 18px avatars on the lane nodes and 24px avatars in the author column, so faces are recognisable at a glance; lists elsewhere stay at the denser 22px.
- **Refs are grouped into one label per branch.** A local branch and its upstream on the same commit are one pill with two icons, plus an up/down count against the upstream. Two pills for the same branch is visual noise; the count is what people actually look for.
- **Relative dates in the graph, exact dates on hover and in the details.** "3 weeks ago" answers the question the column is for; the exact timestamp is one hover away.
- **Solo instead of hide.** Hiding refs one by one is tedious; soloing one or two branches answers "what is on this branch" directly. Esc or the chip in the header brings everything back.
- **The diff is the editor's own diff view.** It runs on Monaco, the open-source core of that editor, so side by side, the +/− gutter, hidden-region folds, the overview ruler and the diagonal fill behave exactly as people expect. A small floating toolbar on each change block stages, unstages or discards that block.
- **Diffs open in a floating window with tabs.** Clicking a file in any list opens it as a tab in one window that can be moved by its title bar, resized from any edge or corner, or maximized; position and size are remembered. The window has no backdrop, so the graph and the file lists stay usable and every file you click becomes another tab. Each tab keeps its own unsaved edits; closing a tab or the window asks first when edits are unsaved. A working-tree tab closes on its own once the file has nothing left to show there, for example after staging the whole file.
- **The working-tree side is editable.** Edits save with ⌘S or the save icon, and the tab shows a dot while there are unsaved edits. Staging writes the chosen block into the index as whole content, not as a patch, so line endings and files without a trailing newline round-trip exactly.
- **Drag a branch label onto a commit** to merge or rebase. A lifted copy of the label follows the pointer while the original fades, the target commit is outlined, and a note under the copy says what the drop will do or why it cannot happen there. The graph scrolls when the pointer nears its edge, and Esc cancels. The drop menu only lists operations that are possible from the current state, and says why when none are, instead of failing after the fact.
- **One command palette, one shortcut list.** Every action in a menu is also in the palette (⌘⇧P) so a keyboard user never has to find a pixel. The shortcut list (?) is generated from the same table that binds the keys, so it cannot drift.
- **Keys typed in the diff stay in the diff.** App shortcuts ignore keystrokes that start inside the diff window, and ⌘S is bound per editor, so a save always writes the file you are looking at. Single-letter staging shortcuts were removed after one staged a file by accident; staging happens from the block toolbar or the file list.
- **Status bar carries the three numbers that change what you do next:** ahead/behind against the upstream, uncommitted changes, stashes. Nothing else.
- **Destructive actions confirm with the consequence, not the verb.** "Unstaged edits to README.md will be lost. Continue?" rather than "Are you sure?".
- **In-progress operations get a banner, not a modal.** A merge, rebase, cherry-pick or revert that stopped on conflicts shows a banner with Continue and Abort, and the conflicted files are marked in the list. The user can keep using the graph while deciding.
- **Trees collapse single-child folders** (`src/ui/components` as one row) so deep paths do not need six clicks.
- **Per-file numbers (+12 −3) sit at the right edge** and give way to the action buttons on hover, so the row never grows.
- **Light theme follows the OS** and can be overridden from the status bar; both palettes keep the same ten lane colours so a branch keeps its colour when the theme changes.
- **Color schemes come from a link.** Pasting a terminalcolors.com theme link applies its background, foreground, accent and sixteen colors. Every other interface color is mixed from those, the branch lanes and git status colors use the sixteen, and the diff and agent terminal use them for syntax and output. It is saved by the helper, so it survives restarts.

## Left out on purpose

- Undo/redo of git operations: the reflog already provides it and a faithful implementation needs state tracking that is easy to get wrong.
- Interactive rebase by dragging commits: valuable, but it needs its own mode and conflict flow; planned as a separate round.
- Integrations with hosting services, cloud patches, AI features: outside the scope of a local client.
